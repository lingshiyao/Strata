# T1 判决书：专家缓存 profile 重排 —— 离线实验结论

**日期**：2026-10-04
**执行者**：041 的项目助手
**范围**：T1-1 阶段 1-A / 1-B / 1-C（采集 → 离线验证 → 离线判决）
**对基线的影响**：**零**。未修改任何基线文件、未启动 8080 服务、未改动任何 profile/JSON/BAT。
可复用脚本归档在 `tools/t1_probe/`；原始数据与 trace 写在本地 `.workbuddy-ai/t1_probe/` 下。

---

## 0. 一句话结论

> **T1（重排专家缓存 profile）应当取消。**
> 引擎的专家缓存**不是静态的**——它带一个自适应层，会按对话实际路由频率淘汰/调入专家。
> 该自适应层已经拿到了这份收益：把静态 profile 换成「用真实路由 trace 训练出的最优排名」，
> 在**真实请求长度**上只多 **约 3 个百分点**命中率，在长会话上只有 **1.1 个百分点**。
> 这与方案原本预期的「+20pt」相差一个数量级——原先的 +20pt 是**忽略自适应层**算出来的静态数字。
>
> 更狠的一条（§4.4）：把静态 profile **整个删掉**、只留「到达顺序入住 + 自适应」，
> 在除最短会话外的所有长度上都 **≥ v1 + 自适应**。即 **静态 profile 本身几乎不产生收益**。

## 1. 做了什么

| 阶段 | 内容 | 产物 |
|---|---|---|
| 1-A | 用 `--dump-routing` 采一条真实编码负载的路由 trace | `trace_decode.bin`（8.64 MB） |
| 1-B | 离线算 v1 profile 的命中率，与生产实测对照 | 见 §3 |
| 1-C | 离线**模拟自适应层**，判断「换更好的 profile」是否还有价值 | 见 §4 / §5 |

### 1.1 采集命令（不碰基线）

```
engine/strata.exe --pack E:/Strata-data/packs/coder-iq1_m
  --native <shard1.gguf> --ple-gguf <shard2.gguf>
  --expert-profile D:/Strata/data/expert-profile-coder.bin   # 只读
  --expert-cache auto --prefill auto --spec 4 --mtp E:/Strata-data/mtp/rt
  --max-context 262144 --kv int8 --kv-resident 32768 --vram-reserve-mib 700
  --pool-workers 15 --tokens-file <2683-token 编码 prompt> --max-new 1600 --greedy
  --dump-routing .workbuddy-ai/t1_probe/trace_decode.bin     # 写到探针目录
```

结果：prompt 2682 tokens（1588 tok/s），生成 1600 tokens（82.27 tok/s），
trace = **98,208 条记录 = 48 层 × 2046 个位置 × 10 专家 = 982,080 次查找**。
prompt 由 4 个 benchmark 编码任务 + 一段 C++ 题拼成，覆盖 4 个不同主题。

### 1.2 三条被源码核实的前提（之前只是推测）

1. **trace 记录的是「全部路由查找」，不是「仅未命中」。**
   `session.cpp:700/703` 把**同一个** `s.db->h_ids`（门铃发布的该层完整路由决策）同时交给
   `hits(...)` 和 `pool(...)`；`drive_pool` 写 trace 时遍历全部 k 个 id，命中项在池里被 memset 成 0
   但仍留在 `ids` 数组里。所以离线命中率代理是**精确**的，不是近似。

2. **profile 二进制格式**：`"STRP"(4B) + <5I>(20B) = 24B 头`，然后 `n` 个 `<HH`（layer, expert）
   构成**有序排名表**（第 i 项 = 第 i 号槽位），再 48×ne 个 int32 反查表。
   `expert-profile-coder.bin` = 24 + 12288×4 + 12288×4 = 98,328 B ✓（反查表自洽性 0 处不一致）。

3. **native IQ pack 的 trace 只能覆盖「生成位置」，覆盖不了 prompt。**
   prompt 走批量 prefill（`src/prefill/` **不写 routing**）；`--prefill-until 1` 是个陷阱——
   它把批量 prefill 截断成 1 个 token，而 native pack 的投机循环（`generate.cpp:5410` 立即
   `break` 到 spec 路径）**不消费剩余 prompt**，结果模型从「单 token 上下文」开始生成。
   （第一次试跑就踩了这个坑，trace 上下文退化，已废弃。）

## 2. 一个必须先说清的发现：引擎缓存是**自适应**的

交接文档、`TUNING_REAUDIT` 以及此前的所有讨论，都把专家缓存当成**静态**的
（「前 N 个排名常驻，no eviction」）。日志确实也这么写：

```
strata generate: expert cache 4161 slots, 7.92 GiB of VRAM; policy is
                 PROFILE, ranked by routing frequency, no eviction.
```

**但 `generate.cpp:5703-5756` 里有一个自适应层，它确实会淘汰：**

```cpp
// Plan v0.3 P6: the VRAM tier follows the conversation.  Candidates are missing experts routed at least
// twice (decayed); each is paired with its layer's least-routed resident expert and swapped when it was
// routed clearly more often.  Copies run between rounds, when the GPU is idle.
```

- 触发：每 `adapt_every = 4` 轮（**参数默认值，未写入 `usage()`，属未文档化开关**）
- 候选 `cand`：未驻留 且 衰减使用率 `>= 2.0`
- 受害者 `vict`：该层**驻留中路由最少**的专家
- 交换条件：`cand.usage >= vict.usage + 1.5`
- 每次最多 `adapt_swaps = 96`（同样未文档化）
- 每轮结束：所有 usage `*= 0.7`（衰减）
- `usage` 累加见 `expert_source.cpp:1610-1612`（每个路由 id +1）

**实测证据**：1600-token 的运行里，引擎自己报告
`adaptive tier  15204 experts swapped into the VRAM tier (every 4 rounds, 0.167 ms/round)`。
4161 个槽位里换手 15,204 次——**缓存不是静态的**。

## 3. 阶段 1-B：v1 的离线静态命中率（与生产实测对照）

| N（槽位） | 对应配置 | v1 离线静态命中率 |
|---|---|---|
| 3629 | baseline `-256k`（reserve 700） | **51.10%** |
| 3793 | `-ultra`（reserve 380） | 52.62% |
| 3835 | `-tuned`（reserve 300） | 52.93% |
| 4161 | 本次运行实际（reserve 700 + MTP） | 55.48% |

**与生产日志对照**：`strata-coder-iq1_m-256k.log` 里 22 条
`decode expert cache hit rate`，范围 49.1%~80.6%，中位约 **70%**。

> 口径说明：引擎报的命中率是**严格口径**——分子只有 `cache_hits`（查到时就已常驻），
> `cache_admitted`（首次入住）只进分母不进分子（`generate.cpp:5221-5222`）。
> 本文 v1/oracle 两臂槽位始终满、不触发 admit，与此口径一致，可直接对照。

**51% vs 70% 的 19 个百分点差，就是自适应层贡献的。** 这一条把整个 T1 的前提推翻了：
原先「v1 只有 51%、最优排名有 75%，所以有 24pt 可捡」的推理，漏掉了自适应层。

## 4. 阶段 1-C：离线模拟自适应层（**与引擎精确吻合**）

按 §2 的源码逻辑写了离线模拟器 `sim_adaptive.py`。

**校准验证**：模拟器在 v1 + 自适应下报出 **15,014 次交换**；引擎真实值 **15,204 次**——
误差 **1.3%**。模拟器可信。

### 4.1 主结果（N = 3629）

| 方案 | 命中率 | 说明 |
|---|---|---|
| v1 **静态** | 51.10% | 原方案看到的数字 |
| **v1 + 自适应** | **75.59%** | ← 真实运行时 |
| oracle(in-sample) 静态 | 75.43% | 用同一条 trace 训练的完美静态排名 |
| **oracle(in-sample) + 自适应** | **76.30%** | ← 换最优 profile 的上限 |
| oracle(仅前半段训练) + 自适应 | 76.67% | held-out 训练也不掉 |
| **随机排名 + 自适应** | **73.54%** | ← 对照：**随便排也能到 73.5%** |
| 随机排名 静态 | 30.59% | |

**读法**：
- 自适应层把 v1 从 51% 抬到 75.6%，**几乎完全吃掉**了到 oracle 静态 75.4% 的全部差距。
- 在自适应之上，换 oracle 只再拿 **+0.71pt**。
- 一个**完全随机**的排名配自适应也能到 73.54%——静态 profile 的内容**几乎不重要**。

### 4.2 会话长度扫描（这才是决定性的表）

生产日志显示每次请求平均约 **385 个 decode 位置**（184800 / 48 / 10）。
自适应需要时间收敛，所以**短请求**里静态 profile 才相对重要：

| T（位置） | v1 静态 | v1+自适应 | oracle+自适应 | 随机+自适应 | **oracle − v1** |
|---|---|---|---|---|---|
| 50 | 57.29% | 60.19% | 65.45% | 37.84% | **+5.26pt** |
| 100 | 57.46% | 64.21% | 70.80% | 45.25% | **+6.59pt** |
| 200 | 57.73% | 69.39% | 73.74% | 53.83% | **+4.34pt** |
| **385（生产典型）** | 56.20% | **73.15%** | **76.10%** | 63.35% | **+2.95pt** |
| 600 | 55.85% | 73.93% | 76.18% | 67.42% | +2.25pt |
| 1000 | 55.22% | 75.02% | 76.79% | 70.98% | +1.77pt |
| 2046 | 51.10% | 75.59% | 76.67% | 73.54% | +1.09pt |

**读法**：
- 在**生产典型长度（385）**上，重排 profile 的收益是 **+2.95pt**。
- 在**长会话**上只有 **+1.09pt**。
- 但 profile 也不是完全没用：同长度下 v1（73.15%）比**随机**（63.35%）高 9.8pt。
  即 **v1 已经是个「及格」的 profile**，离最优只差 3pt。

### 4.3 自适应频率的敏感性（比 profile 更值钱的杠杆）

| `adapt_every`（位置） | v1 | oracle | 差 |
|---|---|---|---|
| 4 | 77.94% | 78.38% | +0.44pt |
| 8 | 76.51% | 77.03% | +0.52pt |
| **13（≈引擎的 4 轮）** | **75.59%** | **76.30%** | **+0.72pt** |
| 26 | 74.21% | 75.35% | +1.14pt |
| 52 | 71.96% | 74.34% | +2.39pt |

**自适应调得越勤，命中率越高**——`adapt_every` 从 13 降到 4（位置）就有 +2.4pt，
比换 profile 的 +0.7pt 更大。而且它是 `--adapt-every` / `--adapt-swaps` 两个**未文档化开关**，
当前三份 JSON 都没设，走默认 4 轮 / 96 次。

### 4.4 「不给 profile」对照组（比 oracle 更狠的一条）

引擎报的命中率是**严格口径**：分子只有 `cache_hits`（查到时就已常驻），
`cache_admitted`（首次使用即入住）**只进分母不进分子**——见 `generate.cpp:5221-5222`：

```cpp
const int64_t req_hits = drive.d.cache_hits - decode_hits0;
const int64_t req_look = (cache_hits + cache_admitted + cache_refused) - decode_look0;
```

即「首次入住」虽然由 GPU 计算、当次算命中，但在**报表口径**里记作 miss。
（§4.1/§4.2 的 v1/oracle 两臂槽位始终满、不触发 admit，所以不受影响；本节的对照臂按此口径实现。）

于是再补一个对照：**完全不给 profile**——缓存从空开始，miss 时若有空槽就按**到达顺序**入住（默认策略
是一个全局共享计数器），再叠加同一个自适应层。

| T（位置） | v1 静态 | v1+自适应 | **不给 profile +自适应** | 随机+自适应 | oracle+自适应 | oracle − v1 |
|---|---|---|---|---|---|---|
| 50 | 57.29% | 60.19% | **68.70%** | 37.84% | 65.45% | +5.26pt |
| 100 | 57.46% | 64.21% | **68.05%** | 45.25% | 70.80% | +6.59pt |
| 200 | 57.73% | 69.39% | **71.05%** | 53.83% | 73.74% | +4.34pt |
| **385（生产典型）** | 56.20% | 73.15% | **74.04%** | 63.35% | 76.10% | +2.95pt |
| 600 | 55.85% | 73.93% | **74.61%** | 67.42% | 76.18% | +2.25pt |
| 1000 | 55.22% | 75.02% | **75.58%** | 70.98% | 76.79% | +1.77pt |
| 1500 | 55.64% | 76.20% | **76.64%** | 73.40% | 77.57% | +1.37pt |
| 2046 | 51.10% | 75.59% | **75.94%** | 73.54% | 76.67% | +1.09pt |

**读法**：把静态 profile **整个删掉**、只留「到达顺序入住 + 自适应」，
在**除最短会话外的所有长度上都 ≥ v1 + 自适应**（385 位置：74.04% vs 73.15%），
并且几乎追平 oracle（76.10%）。原因很直白：到达顺序**本身就是**对当前负载的一阶自适应，
而静态 profile 预填的是一批「可能是错的」专家，自适应层还得先把它们换出去。

> ⚠️ 这条是**模拟结论**，未做真机验证；且 `--resident-cpu-experts` 的低内存模式需要静态 profile
> 来定义「补集」（好让交换不回读文件），所以「删掉 profile」不是无脑可用的建议。
> 但它把 §4 的结论从「换 profile 收益小」推进到「**静态 profile 本身几乎不产生收益**」。

## 5. 结论与建议

### 5.1 T1 判决：**取消**

| 项 | 原方案预期 | 实测 |
|---|---|---|
| 静态排名可提升 | +24pt（in-sample） | 成立（51.1% → 75.4%） |
| **运行时**可提升 | 隐含 +20pt | **+0.7pt（长会话）～ +3.0pt（385 位置）** |
| 值不值得做 bin/json/bat + 真机 A/B | 值 | **不值** |

**理由**：自适应层已经把这份收益拿到了。做 T1 的工程（新 bin + 新 json + 新 bat + 一次 A/B）
能换到的是**约 3 个百分点命中率**，折算到速度大约 **3~5%**（池耗时 12.1 ms/轮，
命中率 73%→76% 意味着 miss 减少 ~11%，约省 1.3 ms/轮，占 30.6 ms/轮的 ~4%）。
考虑噪声和「单条 trace 单种负载」的外推风险，这个量级不值得作为第一优先。

### 5.2 顺手排除掉的：交接文档 / README 的一处错误

`bench/results/2026-09-28-coder/README.md` 称 `data/expert-profile-coder.bin` 是
「the shipped 48 x 512 ranking re-indexed」。

**这不成立**。实测：

- coder profile（48×256）与出厂 profile（48×512）的**序相关 Kendall tau = +0.0032**
  ——「重新索引」不会改变顺序（tau 应为 ±1），tau≈0 说明两者是**相互独立**的排名。
- coder 排名**不是** base 排名的保序子序列（0/48 层单调）。
- coder 元素在 base 排名中的位置遍布 0~471（中位 ~240），不是前缀、不是等间隔、不是最小/最大子集。
- 两者 top-3629 集合重合仅 **15.0%**。

（该文件由 Niko1221 于 2026-09-28 的 `b12ab01`「The GSQ-RCO Coder (256 of 512 experts): setup,
profile, speeds (PR #54)」一次性引入，此后未再改动。所以 README 描述的就是这个文件——
即 **README 的说法与文件实际内容不符**。真实来源未知，但可以确定它**不是**简单的重新索引。）

→ 该结论对 T1 的判定无影响（§4 已经说明无论来源如何都没有提升空间），
但**建议修正 README**，因为它会误导后来者以为「coder profile 是通用排名」。

### 5.3 建议的下一步优先级（替代 T1）

| 优先级 | 项目 | 依据 | 预期 |
|---|---|---|---|
| **新 T1** | **自适应层参数扫描**：`--adapt-every` / `--adapt-swaps` | §4.3：13→4 位置 +2.4pt，比 profile 的 +0.7pt 大 | 命中率 +2~3pt；**但要看它挤占的 0.167 ms/轮拷贝成本** |
| T2 | PLE I/O（`--ple-io` / `--ple-row-cache` / `--ple-inflight`） | 未触及 | 未知 |
| T3 | MTP 重扫（接受率仅 44~65%） | 未触及 | 未知 |
| T4 | 智商线（补 budget=0/32768/49152 三臂） | 未触及 | 未知 |
| ~~T1~~ | ~~profile 重排~~ | **本报告 §4** | **取消** |

### 5.4 本次实验的局限（诚实标注）

1. **单一负载**：trace 来自一次 1600-token 生成（4 个编码任务作上下文）。
   生产是多次不同主题的短会话。自适应在**主题频繁切换**的真实负载上会更弱，
   那时静态 profile 的相对价值会**略高**于本报告的数字。
2. **长度换算近似**：模拟器用「位置」代替引擎的「轮」，靠交换次数校准（15,014 vs 15,204）。
   绝对值可信，边际比较更可信。
3. **in-sample oracle 是上界**：held-out 版本（仅前半段训练）反而略高（76.67%），
   说明这条 trace 内部自相似度高，oracle 的优势里有一部分是「同一条生成的自相似」，
   真实跨主题负载上 oracle 的优势应**小于**本报告。
